# Правила проекта (AGENTS.md)

## Дизайн и UI/UX

- **ОБЯЗАТЕЛЬНО:** Перед созданием или изменением интерфейса читать и соблюдать
  [design.md](design.md). Этот документ содержит все правила дизайна и UI/UX
  проекта: оформление модальных окон, фирменные узоры, тексты, i18n,
  подтверждения действий и условия многоагентной приёмки.
- Правила из `design.md` обязательны наравне с этим файлом. Изменения стандарта
  дизайна вносить в `design.md`, не дублировать их в `AGENTS.md`.

## Code Structure Rules

### Рекламные страницы курсов
- Основные страницы сайта `01academy.uz/[locale]/courses/[courseId]` и рекламные
  `01academy.uz/[locale]/meta/courses/[courseId]` должны изменяться совместно.
  Содержание, оформление и формы используют общий шаблон сайта; независимые
  расходящиеся копии запрещены. При изменении интеграции заявок проверять обе версии.
  При переименовании курса также синхронизировать `shared/meta-website-leads.ts`
  и `server/services/website-lead-comment.ts`.
- Каждая отдельная отправка рекламной формы учитывается как заявка Meta, в том
  числе для существующего контакта. Сетевой повтор одного `submissionId` не является
  новой заявкой. Платежи, выручка и уникальные контакты не дублируются.

### 1. Архитектура и качество кода
- Руководствоваться архитектурными правилами из `docs/architecture.md` (`npm run check:architecture`).
- Разделять код по самостоятельным обязанностям, пользовательским сценариям и слоям.
- **ЗАПРЕЩЕНО:** Искусственно сжимать форматирование, дробить связную логику или удалять полезные комментарии ради формальных лимитов. Нарушения направления зависимостей и циклические импорты — блокирующие ошибки.

## Git & Deployment Rules

### 1. Автоматический коммит и пуш в `main` на GitHub
- **ОБЯЗАТЕЛЬНО:** После завершения задачи автоматически отправлять изменения в GitHub напрямую в ветку `main` (`git add .`, `git commit -m "..."`, `git push origin main`).
- **ЗАПРЕЩЕНО:** Создавать отдельные feature branches без явной просьбы пользователя.
- Если удаленный репозиторий не настроен или нет доступа, немедленно запросить подключение у пользователя.

## Testing & Verification Rules

### 1. Локальные тесты и CI
- **ОБЯЗАТЕЛЬНО:** Локально запускать **только тесты затронутых и связанных сценариев** (например, `npm test -- tests/lead-social-accounts.test.ts`).
- **ЗАПРЕЩЕНО:** Запускать полный локальный набор `npm test` без фильтра по умолчанию (полный набор тестов всегда выполняется в GitHub Actions перед деплоем).
- При изменении только документации или инструкций тесты не запускать; проверять `git diff --check`.
- Полный набор тестов и проверки в CI не отключать и не обходить.

### 2. Согласование браузерных проверок (Browser Agent Permission)
- **ОБЯЗАТЕЛЬНО:** Предварительно запросить явное разрешение пользователя в чате перед открытием браузера, запуском браузерных агентов или созданием скриншотов.
- **ЗАПРЕЩЕНО:** Открывать браузер или выполнять автоматизированные браузерные проверки без прямого согласия пользователя.

## Database & Migration Rules

### 1. Доступы для миграций БД
- **ОБЯЗАТЕЛЬНО:** Запрашивать логин и пароль к БД/серверу перед запуском миграций на боевом/удаленном сервере.
- **ЗАПРЕЩЕНО:** Автоматически накатывать миграции на продакшене без подтвержденных доступов.

### 2. Создание учебных групп в БД (Course Group Naming)
- **ОБЯЗАТЕЛЬНО:** При создании групп напрямую в БД код обязан иметь формат:
  `[ФИЛИАЛ-ИЛИ-ОНЛАЙН]-[КУРС]-[ТИП]-[ГОД]-[НОМЕР]` (например, `CYP-VC-GRP-26-0001`).
  - Филиал: `CYP` (Cyberpark) или `ONL` (онлайн).
  - Тип: `GRP` (групповой), `IND` (индивидуальный).
  - Год: 2 цифры (например, `26`).
  - Порядковый номер: глобальный сквозной 4-значный `0001, 0002...` (`max + 1` среди всех существующих групп в БД, включая архивные).
- Перед вставкой проверять актуальный максимум номеров на отсутствие коллизий. Полная спецификация и утверждённые коды курсов: `docs/course-group-naming.md`.
