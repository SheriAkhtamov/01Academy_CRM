# Внешние резервные копии CRM

Production-сервер создаёт каждый час полный ZIP с PostgreSQL dump и каталогом
`uploads/`. Отдельный физический сервер самостоятельно забирает опубликованные
архивы. Production-сервер не имеет ключа и прав доступа к физическому серверу.

## Согласованность базы и вложений

После фиксации удаления вложения CRM сначала сохраняет его неизменяемые байты
в `uploads/.retained/` по исходному относительному пути и только затем удаляет
рабочий файл. Если сохранить копию не удалось, рабочий файл остаётся на диске.
Неудачные, не сохранённые в базе загрузки такой копии не требуют.

Резервное копирование выполняет PostgreSQL dump, копирует рабочие файлы в
отдельный временный каталог, затем добавляет сохранённые удалённые файлы без
перезаписи уже скопированных. ZIP, размеры, число файлов и `uploads.sha256`
строятся из этого стабильного каталога. Ошибка копирования прерывает публикацию.
Это позволяет восстановить файл, ссылка на который была в снимке базы до
параллельного удаления. Временный `.retention-work/` в архив не попадает.

Каталог `.retained/` намеренно не очищается scheduler-контейнером: он имеет
доступ к uploads только для чтения. Для ограничения объёма оператор может
запускать `scripts/prune-retained-uploads.sh` на production-хосте с доступом на
запись и окружением резервного копирования, либо явно запускать
`/usr/local/bin/prune-retained-uploads` из backup image в отдельном operator job.
Для этого job нужны uploads с доступом **на запись** и тот же каталог backups,
которым пользуется scheduler. Постоянный scheduler сохраняет read-only uploads.
Этот скрипт берёт ту же блокировку
`BACKUP_DIR/.backup.lock`, создаёт свежую проверенную копию и лишь после её
успешной публикации удаляет retained-файлы старше `RETAINED_UPLOAD_KEEP_DAYS`
(по умолчанию 30 дней). Он использует **ctime**, обновляемое при сохранении
удалённого файла, а не исходное mtime. Не удаляйте `.retained/` другими командами
или одновременно с созданием backup. Без запуска обслуживания каталог растёт.
При настройке любых будущих сборщиков несохранённых загрузок оставляйте
минимум 10 минут для завершения запроса и транзакции.

## Хранение

- production-сервер: последние 10 полных архивов;
- физический сервер, `/srv/backups/01academy-crm/hourly`: все ежечасные архивы
  за последние 90 дней;
- физический сервер, `/srv/backups/01academy-crm/monthly`: по одной копии за
  первое число каждого месяца, без ограничения срока хранения.

Ежечасная история ограничена `RETENTION_DAYS=90`. После каждой успешной
передачи локальный root-этап сначала сохраняет месячные копии и лишь затем
удаляет ежечасные архивы, достигшие этого возраста, вместе с их контрольными
суммами. Граница считается по точному времени без округления до полных суток.

Для каждого месяца выбирается первая доступная копия, созданная первого числа
по времени Ташкента (`MONTHLY_BACKUP_TIME_ZONE=Asia/Tashkent`). Дата берётся
из UTC-времени в имени архива с переводом в этот часовой пояс: например,
`20260930T195351Z` соответствует 1 октября, 00:53:51. Правило применяется
и к уже накопленной ежечасной истории. Если копии за первое число нет,
архив другого дня не подставляется вместо неё.

Месячный ZIP копируется в отдельный каталог вместе с исходной контрольной
суммой, проверяется и остаётся навсегда. Повторные запуски и запоздало полученные
более ранние копии не заменяют уже принятую месячную копию. Ошибка сохранения
или контрольной суммы прерывает очистку ежечасной истории. Общая блокировка
`.vault.lock` защищает публикацию и удаление от одновременной ежедневной проверки.
Месячный каталог принадлежит root и недоступен службе получения на запись.
База и загруженные файлы находятся в одном ZIP; обе политики применяются к ним
вместе.

При обновлении существующей установки перед загрузкой новых systemd units
подготовить каталог, блокировку и модуль месячного хранения:

```bash
sudo install -d -o root -g crmbackup -m 0750 /srv/backups/01academy-crm/monthly
sudo touch /srv/backups/01academy-crm/.vault.lock
sudo chown root:crmbackup /srv/backups/01academy-crm/.vault.lock
sudo chmod 0640 /srv/backups/01academy-crm/.vault.lock
sudo install -o root -g crmbackup -m 0640 scripts/lib/offsite-monthly-backups.py /opt/01academy-backup/bin/offsite-monthly-backups.py
```

Обновить finalizer, audit, обе службы и окружение из `ops/systemd`, затем выполнить
`sudo systemctl daemon-reload`. Модулю нужен Python 3.9+ с системной базой часовых
поясов; дополнительная библиотека Python не требуется. Не заменять существующий
файл блокировки новым inode во время работы служб.

Каталог с программой находится в `/opt/01academy-backup` и принадлежит `root`.
Обычные Ubuntu-пользователи не могут прочитать, изменить или удалить программу,
конфигурацию, SSH-ключ и архивы. Администратор `sheri` получает доступ только
через `sudo`. Системная учётная запись `crmbackup` не имеет пароля, login-shell,
`sudo` и доступа к Docker.

SSH-ключ хранится в зашифрованном systemd credential, одновременно привязанном
к установке Ubuntu и аппаратному TPM 2.0, и раскрывается службе только на время
запуска. После проверки новый архив немедленно переходит во владение `root`.
Служба может читать принятую историю для контроля целостности, но sticky-каталог
и root-владение запрещают ей изменять, переименовывать и удалять ранее принятые
файлы. Очистку 90-дневной истории выполняет отдельный локальный root-этап после
успешной проверки.

Каждый день отдельная служба без сети и без прав записи повторно проверяет все
ежечасные и месячные архивы, их права, SHA-256, структуру ZIP, манифест и читаемость
PostgreSQL dump. Свежесть контролируется по последней ежечасной копии; возраст
месячных архивов не ограничен.
Результат сохраняется в `/var/lib/crmbackup/state/vault-audit.last-success`.

Перед сохранением физический сервер независимо проверяет:

- внешнюю SHA-256 сумму ZIP;
- целостность ZIP;
- наличие `database.dump`, `manifest.json` и `uploads/`;
- SHA-256 дампа из манифеста;
- читаемость PostgreSQL custom dump через `pg_restore --list`.

Архивы удаляются на физическом сервере только его локальным скриптом ротации.
Удаление или компрометация production-сервера не распространяется на уже
полученную внешнюю историю.

## Проверка состояния

На физическом сервере:

```bash
sudo systemctl status 01academy-offsite-backup.timer
sudo systemctl status 01academy-offsite-backup.service
sudo systemctl status 01academy-offsite-backup-audit.timer
sudo systemctl status 01academy-offsite-backup-audit.service
sudo journalctl -u 01academy-offsite-backup.service -n 100 --no-pager
sudo journalctl -u 01academy-offsite-backup-audit.service -n 100 --no-pager
sudo cat /var/lib/crmbackup/state/last-success
sudo cat /var/lib/crmbackup/state/vault-audit.last-success
sudo ls -lh /srv/backups/01academy-crm/hourly
sudo ls -lh /srv/backups/01academy-crm/monthly
```

Ручной безопасный запуск:

```bash
sudo systemctl start 01academy-offsite-backup.service
```

## Восстановление

Сначала скопировать выбранный архив в отдельный рабочий каталог и проверить
контрольную сумму. Восстановление всегда проверять на временной базе, не
перезаписывая действующую production-базу.

```bash
cd /srv/backups/01academy-crm/hourly
sha256sum -c academy-crm-backup-YYYYMMDDTHHMMSSZ.zip.sha256
unzip academy-crm-backup-YYYYMMDDTHHMMSSZ.zip -d /tmp/academy-crm-restore
pg_restore --list /tmp/academy-crm-restore/database.dump >/dev/null
# Для архивов с uploads.sha256 проверить также каждый восстановленный файл:
cd /tmp/academy-crm-restore
sha256sum -c uploads.sha256
```

Физический сервер сейчас использует один линейный LVM-том поверх нескольких
дисков. Такой том не имеет отказоустойчивости: выход любого диска может повредить
весь том. Для окончательной схемы 3-2-1 нужна ещё одна зашифрованная копия либо
перевод backup-хранилища на зеркальный RAID/ZFS.
