**Подробности и варианты реализации**

**UX-01 · P1 — Оплата расхода подменяет выбранный способ оплаты**

Сценарий: Создать запланированный расход со способом «Наличные», затем нажать «Оплатить» и подтвердить.

Доказательство: Форма позволяет выбрать способ оплаты, но при последующей оплате отправляет method: transfer. Обработчик оплаты принимает это значение и заменяет ранее сохранённый способ. В подтверждении показаны название и сумма, но способ оплаты не показан. Источники: [client/src/pages/finance-center.tsx:269](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/pages/finance-center.tsx#L269), [client/src/pages/finance-center.tsx:745](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/pages/finance-center.tsx#L745), [server/routes/finance.routes.ts:691](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/server/routes/finance.routes.ts#L691).

Последствие: Пользователь подтверждает операцию, которая меняет ещё одно поле без его ведома. Финансовые отчёты получают неверный способ оплаты.

Варианты исправления: В AlertDialog добавить Select «Способ оплаты» с текущим значением расхода и показывать выбранный способ рядом с суммой. Более простой вариант — сохранять прежний способ, а его изменение выполнять явно в отдельном Dialog. Для массовой выплаты зарплат также показывать и позволять выбрать способ: сейчас там тоже всегда transfer.

Проверка: Подтверждено чтением полного пути: форма → запрос оплаты → обработчик сохранения.

**UX-02 · P1 — Несохранённый статус ученика теряется при закрытии карточки**

Сценарий: Изменить статус ученика и причину, затем закрыть Sheet крестиком, Escape или перейти к записи оплаты.

Доказательство: Sheet вызывает onOpenChange напрямую. Для statusDraft и exitReason нет проверки несохранённых изменений. После закрытия эффект возвращает значения из записи ученика. Кнопка записи оплаты также напрямую закрывает карточку. Источники: [client/src/components/ux/StudentDetailSheet.tsx:109](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/components/ux/StudentDetailSheet.tsx#L109), [client/src/components/ux/StudentDetailSheet.tsx:201](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/components/ux/StudentDetailSheet.tsx#L201), [client/src/components/ux/StudentDetailSheet.tsx:331](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/components/ux/StudentDetailSheet.tsx#L331).

Последствие: Менеджер теряет введённые изменения и может ошибочно считать, что статус уже обновлён.

Варианты исправления: Использовать useUnsavedChangesGuard и UnsavedChangesDialog для закрытия, навигации и перехода к оплате. Внутри Sheet показывать состояние «Есть изменения» и оставить явную кнопку сохранения. Альтернатива — отдельный Dialog изменения статуса с той же защитой.

Проверка: DOM-проверка: после изменения статуса крестик вызвал onOpenChange(false), AlertDialog не появился.

**UX-03 · P1 — Внешнее обновление ученика молча перезаписывает правки менеджера**

Сценарий: Менеджер выбирает новый статус, пока другой сотрудник меняет статус того же ученика; данные карточки обновляются.

Доказательство: Изменение сочетания id/status/exitReason в полученной записи сразу вызывает setStatusDraft и setExitReason. Наличие локальных правок не проверяется. Родитель передаёт актуальную запись из списка учеников. Источники: [client/src/components/ux/StudentDetailSheet.tsx:107](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/components/ux/StudentDetailSheet.tsx#L107), [client/src/pages/sales-dashboard.tsx:1545](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/pages/sales-dashboard.tsx#L1545).

Последствие: Правки исчезают во время работы, даже если пользователь не закрывал окно.

Варианты исправления: Сохранять локальный черновик до явного решения пользователя. При конфликте внутри Sheet показать Alert с предметными изменениями и кнопками «Сохранить мои изменения» / «Принять изменения». Более безопасный вариант — Dialog сравнения полей перед повторным сохранением.

Проверка: DOM-проверка: локальный paused после обновления props стал completed, подтверждение не появилось.

**UX-04 · P1 — Создание задачи защищено от закрытия окна, но не от ухода со страницы**

Сценарий: Заполнить новую задачу и обновить вкладку либо перейти через навигацию CRM в другой раздел.

Доказательство: CreateTaskDialog проверяет черновик только в handleOpenChange. Компонент не регистрирует общий navigation guard и beforeunload. Переход, размонтирующий страницу задач, не вызывает этот обработчик. Источники: [client/src/components/ux/board/CreateTaskDialog.tsx:175](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/components/ux/board/CreateTaskDialog.tsx#L175), [client/src/pages/tasks.tsx:480](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/pages/tasks.tsx#L480), [client/src/components/ux/UnsavedChangesGuard.tsx:64](https://github.com/SheriAkhtamov/01Academy_CRM/blob/b279c73f2d647ca461fad7065e4712ce23eae753/client/src/components/ux/UnsavedChangesGuard.tsx#L64).

Последствие: Название, описание, выбранные файлы и остальные поля теряются без предупреждения. Поведение отличается от редактирования уже созданной задачи.

Варианты исправления: Подключить общий useUnsavedChangesGuard, сохранив существующий AlertDialog для частично созданной задачи. Опционально сохранять несекретный черновик между переходами; выбранные файлы требуют отдельного продуманного поведения.

Проверка: DOM-проверка: для заполненного черновика событие beforeunload осталось без preventDefault. Проверка регистрации навигационного guard — по коду.
