# Голосовые напоминания о демо

## Статус на 13 октября 2026 года

Реализованы настройки и загрузка записи в модальном окне OnlinePBX, очередь
напоминаний, два параллельных исполнителя, общий резерв каналов с менеджерами,
отмена при переносе демо или изменении участника и журнал результатов.
По умолчанию напоминания выключены. Пользователь подтвердил, что оба менеджера
звонят и принимают звонки только через CRM. Поэтому источник занятости —
сохранённые события CRM, резервы исходящих звонков и отдельные квитанции робота.
Источник подключён через `CrmCapacitySource` в composition root. Неизвестное
состояние отклоняет включение и новые звонки робота.

Робот использует существующих пользователей 100 и 101 с отдельными Verto
сессиями. Новые рабочие места и автоинформатор не подключаются. Учёт каналов
ограничивает суммарную работу менеджеров и роботов двумя внешними звонками.
Освободившийся исполнитель сразу берёт следующее задание, пока второй звонок
продолжается. Неизвестная занятость закрывает допуск роботу.

Успешный тест на разрешённом пользователем номере подтвердил воспроизведение
аудио через OnlinePBX. Пользователь подтвердил слышимость сигнала. Исправлена
совместимость с SDP OnlinePBX без `a=mid`; воспроизведение начинается только
после ответа и установки ICE/DTLS. Статус «Воспроизведено» означает передачу
полной записи, а не доказательство того, что человек её прослушал.

## Учёт занятости внутри CRM

Перед звонком менеджера CRM получает резерв и отдельно подтверждает право
начать вызов с тем же UUID. Менеджеры и роботы используют общий mutex
PostgreSQL и повторно читают занятость внутри транзакции. Это предотвращает
одновременную выдачу одного свободного канала двум исполнителям.

Просроченный резерв, по которому вызов ещё не разрешён, можно освободить:
клиент не начнёт звонок без действующего разрешения. Разрешённый вызов
сохраняется до подтверждения завершения, даже если браузер закрылся или
перестал продлевать резерв. События звонка и запросы освобождения сохраняются
в браузере и повторяются после восстановления связи. Это не прерывает
разговор менеджера при временном сбое CRM.

Для робота подтверждением завершения служит собственный `verto.bye`, ответ
АТС на его запрос завершения либо завершённая запись HTTP-истории с точным
UUID. Разрыв WebSocket и окончание срока резерва сами по себе не доказывают
освобождение канала. Неоднозначное состояние откладывает очередь.

Старые записи CRM сверяются с завершённой историей OnlinePBX вне транзакции
допуска. История может появляться с задержкой, поэтому восстановление допуска
тоже может занять некоторое время. Входящий звонок без определённого
менеджера сохраняет занятость маршрута до его принятия или завершения.
После старта сервера робот ждёт 45 секунд для восстановления сохранённых
событий браузеров; активные звонки отправляют статус каждые 30 секунд,
неподтверждённые события повторяются каждые 5 секунд.
Исходящие звонки связываются по UUID; позднее сообщение о завершении не
связывается с новым разговором только по совпадению номера телефона.

Эта схема рассчитана на согласованное условие «все звонки через CRM». Она
не учитывает новые звонки из сторонних приложений или IP-телефонов. Если
способ работы изменится, источник занятости нужно пересмотреть.
Одновременная потеря входящего webhook и связи браузера с CRM может задержать
учёт нового входящего звонка. Ограничение двух внешних каналов также остаётся
на стороне OnlinePBX; отказ АТС откладывает либо завершает попытку по её исходу.

## Проверка OnlinePBX

Официальная [документация API](https://onlinepbx.evateam.ru/docs/docs/DOC-000051#api)
направляет на [WebSockets API 3.0](https://pbx38153.onpbx.ru:3342/documentation/index.html).
Живая проверка показала, что подписка передаёт новые события, но не даёт
полного начального снимка при подключении во время уже идущего разговора.
SIP BLF также не отразил активный Verto-звонок. Эти источники не используются
как доказательство свободных каналов. Запрос в поддержку не требуется при
подтверждённом пользователем режиме работы только через CRM и не отправлялся.

## Условия активации

1. Восстановить старые незавершённые записи журнала. На сервере обнаружены
   16 записей со статусами dialing/ringing, из которых 15 начались до
   12 октября. Их прежние browser UUID не всегда совпадают с UUID истории
   АТС. Автоматически освобождать их только по возрасту нельзя; восстановление
   исходной базы занятости требует подтверждения фактического завершения.
   Количество больше двух считается противоречивым состоянием и закрывает
   допуск очереди. Новые события защищены durable outbox и резервами.
2. Загрузить запись пользователя и выбрать время напоминания и разрешённые
   часы в CRM. Аудио хранится в приватном каталоге uploads/voice-reminders.
3. Включить напоминания после загрузки записи. Настройки доступны руководителям.
   Без записи очередь не включается. Тестовое воспроизведение уже подтверждено
   пользователем на его номере; звонки клиентам без рабочей записи не запускались.

Миграции `0142_voice_reminders.sql` и `0143_crm_telephony_capacity.sql` запускаются обычным CI/deploy процессом до
старта сервера. Очередь использует PostgreSQL leases, отменяет устаревшие
задания и не повторяет неоднозначные попытки после падения процесса. Callback
робота перехватывается до создания контакта и атрибуции менеджеру; неоднозначные
callback сохраняются отдельно и не увеличивают KPI менеджеров.

Локально запускать только тесты voice-reminders, voice-verto, voice-provider,
voice-telephony-webhook, telephony-channel-reservations и затронутые сценарии
менеджерского телефона. Полный набор выполняется в GitHub Actions.
